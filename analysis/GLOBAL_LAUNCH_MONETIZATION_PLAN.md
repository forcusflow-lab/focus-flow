# Focus Flow 世界公開・収益化計画

> **前提と留意事項**：これは2026年8月13日時点の公開情報と現行プロダクトを基にした事業・価格設計の叩き台であり、売上やストア審査通過を保証するものではありません。アクセシビリティAPI、プライバシー、消費者保護、税務、決済に関わる最終判断は、公開地域に対応できる専門家と各ストアの最新ポリシーで確認してください。

## 1. 結論：Android-firstで「完了が先、解放が後」を売る

Focus Flowは、一般的なTodoアプリでも単なるアプリブロッカーでもなく、**「今日の自分との約束を終えたら、選んだ気晴らしアプリを使える」**という行動設計を中核価値に据えるべきです。最初の商用版は、アプリ制限機能が完成している**Androidに集中**します。iOS版は、まずTodo・習慣・メモ・日課ルールを中心とした補助版として扱い、同等の制限を約束しません。

iOSでScreen Time系の制限を配布するにはFamily Controlsの配布用entitlementが必要であり、AppleのフレームワークはFamily Controls、Managed Settings、Device Activityを前提にしています。[1] [2] Androidのアクセシビリティ方式と同じ挙動を短期間で移植する前提は、事業上も技術上も危険です。したがって、最初の12か月は**Androidで価値と継続率を実証し、iOSは意図的に機能差を説明した上で後追い**にします。

| 項目 | 推奨方針 | 理由 |
| --- | --- | --- |
| 初期プラットフォーム | Android / Google Play | 現在完成している必須Todo・習慣連動のアプリ制限を、そのまま検証できる。 |
| 主な対象者 | 自己管理したい学生、知識労働者、クリエイター | 「タスクを終えてからSNS・動画・ゲームを開く」価値が一文で伝わる。 |
| 差別化 | 完了条件連動の制限、数値進捗、日課ルール、ローカル優先 | タイマー中心・単純ブロック中心の競合と明確に異なる。 |
| 初期地域・言語 | 英語版を主軸に、既存の日本語を維持 | ASO、サポート、開示文言を2言語に絞り、学習速度を優先する。 |
| iOSの扱い | Companion版から開始 | 期待値をコントロールし、entitlement取得後に制限機能を検討する。 |

## 2. 公開前に解くべき最大の課題：信頼とストア適合

Focus Flowの競争優位になり得るアクセシビリティサービスは、同時に公開上の最大リスクです。Google Playでは、AccessibilityService APIを使うAndroid 12以降向けアプリにPermissions Declaration Formと承認が求められます。アクセシビリティツールとして適格でないアプリには、アプリ内の目立つ独立した開示と、明示的な同意も必要です。[3] このため、公開を急ぐよりも、**「何を読むか、何を保存しないか、なぜ必要か、いつ解除できるか」**をUI・ポリシー・審査資料のすべてで一致させることが先決です。

### 2.1 必須の信頼設計

| 領域 | リリース前の要件 | 完了基準 |
| --- | --- | --- |
| アクセシビリティ開示 | 初回設定の通常フローで、前面アプリのパッケージ名を制限判定に用いる理由、端末外へ送らない方針、無効化手順を単独画面で説明する。 | 同意チェック後にだけAndroid設定へ遷移し、拒否してもTodo・習慣機能を使える。 |
| 権限最小化 | `AccessibilityService`、アプリ選択、Widgetに必要な情報だけを使う。インストール済みアプリ一覧・アクセス状況を分析SDKへ送らない。 | プライバシー棚卸しにデータ流出経路がない。 |
| フェイルオープン | 状態が壊れた、サービスが無効、時刻判定が不確実などの場合に、端末を利用不能にしない。 | 障害試験で無限リダイレクト、自己アプリのブロック、システムUIの妨害がない。 |
| 審査資料 | Play ConsoleのAccessibility declaration、短い機能動画、開示画面のスクリーンショット、テスト用手順を用意する。 | 審査者が3分以内に機能・同意・解除を再現できる。 |
| Data safety | 自アプリとSDKのデータ取扱いを棚卸しし、Data safety formとプライバシーポリシーを一致させる。 | 「データを収集しない」場合もポリシーURLとフォームを提出する。 |

Google PlayのData safetyは、公開アプリの開発者がアプリと第三者SDKを含むデータ収集・共有を申告する仕組みであり、データを収集しないアプリでもフォームとプライバシーポリシーが必要です。[4] また、AccessibilityServiceや広範なアプリ可視性は、Data safety上のApp activity・Installed appsに関わり得ます。[5] **「ローカル保存だから申告不要」とは判断しない**で、ビルド済みアプリと依存SDKを基に項目を確認します。

### 2.2 公開前チェックリスト

1. アクセシビリティの同意画面、プライバシーポリシー、ヘルプ、ストア説明の表現を英語・日本語で揃える。
2. 「他アプリを完全にロックする」「絶対に解除不能」といった主張を避け、「選択したアプリへの移動を補助的に制限する」と表現する。
3. `pnpm test`、型検査、Lint、Android prebuild、実機でのサービス有効・無効・スケジュール境界・再起動・Widget・誤設定を検証する。
4. 問い合わせ用メールアドレス、プライバシーポリシー、利用規約、返金・解約案内、障害時の解除手順を公開する。
5. 課金前に、ユーザーが「必須項目を作る → 制限対象を選ぶ → 権限を有効にする → 今日1件を達成する」の価値体験を完結できることを確認する。

## 3. 収益化モデル：価値を体験させ、拡張性に課金する

最初は**広告を入れないフリーミアム + 年額中心のサブスクリプション**を推奨します。注意・集中を売るアプリに広告を入れると、信頼と集中の双方を損なうためです。競合のAppBlockは無料枠にスケジュール数や対象数の上限を置き、7日間の試用と月額・年額・買い切りを併用しています。[6] Freedomは年額換算で月額$3.33、月額$8.99、7日間試用を提示し、Opalは1ルールの無料枠と年額$99.99のProを提供しています。[7] [8]

これらは価格の正解ではなく、**無料で中核価値を示し、継続的な自動化・複数ルール・強化機能に課金する**ことが、このカテゴリで一般的な設計であることを示します。Focus Flowは市場の上限を追わず、初期は低摩擦の年額プランで継続率を検証します。

| プラン | 推奨初期価格（USD） | 提供価値 | 意図 |
| --- | ---: | --- | --- |
| Free | $0 | 通常Todo・習慣・メモ、必須項目、1つの日課ルール、最大3つの制限対象アプリ、ローカル保存 | 「今日の約束を終えて1つの気晴らしアプリを解放する」体験を完結させる。 |
| Focus Flow Plus 月額 | $4.99 / 月 | 無制限のルール・対象アプリ、複数時間帯、詳細な数値目標、反復Todo、サブタスク、外観設定、Widget | ヘビーユーザーの柔軟性と継続利用に課金する。 |
| Focus Flow Plus 年額 | $29.99 / 年 | 月額と同内容、7日間無料体験 | 年額を主提案にして継続利用を促し、単月の解約摩擦を減らす。 |

**初期は買い切りを出さない**ことを推奨します。サポート・OS追従・ポリシー対応が継続発生する制限機能では、買い切りが将来の保守原資を先に固定してしまうためです。買い切りは、年額の更新率、サポート負荷、継続コストが見えた6〜12か月後に限定キャンペーンとして評価します。

Google Play配布版で、Plusのようなデジタル機能・サブスクリプションをアプリ内で販売するなら、原則としてGoogle Playの課金システムを使う必要があります。[9] 初期は外部決済導線を混在させず、Play Billingのみで始め、地域別制度やWeb販売は成長後に専門家と個別に検討します。

## 4. 90日ローンチ計画

### Phase A：公開可能性の確立（Day 0–21）

この期間の成果物は、機能追加ではなく**審査・信頼・検証の土台**です。Privacy Policy、Terms、Accessibility disclosure、サポート導線、英語ストア素材、Play Billingのテスト商品、クラッシュ報告を準備します。課金を先に有効化するのではなく、無料フローの到達率を測れるイベント設計を先に入れます。

| 実装・運用項目 | 優先度 | 合格条件 |
| --- | --- | --- |
| 英語UIとストア素材 | P0 | プロダクト名、説明、権限説明、課金文言、空状態が自然な英語で統一される。 |
| 計測設計 | P0 | 個人メモやタスク本文を送らず、匿名化したフローイベントだけで活性化を測る。 |
| 課金基盤 | P0 | テスト購入、復元、解約後の権限、試用終了、オフライン時の表示を検証する。 |
| 審査パッケージ | P0 | declaration、開示画面、手順、動画、テストアカウント不要の説明が揃う。 |
| サポート運用 | P1 | 24〜48時間以内の一次返信、アクセスビリティ解除のFAQ、返金・解約リンクを用意する。 |

### Phase B：クローズドベータ（Day 22–45）

まずはAndroid利用者30〜60人を、学生・知識労働者・自己管理目的のユーザーに分けて募集します。Google Playのinternal testは最大100人の招待テスターに短時間で配布でき、closed testは公開評価に影響しない個別フィードバックを集められます。[10] [11] この段階では、広告購入ではなく、ユーザーインタビュー、障害報告、再現動画、週次アンケートから価値仮説を検証します。

ベータの最重要質問は「ブロックできるか」ではなく、**“今日は必要な行動を終えられた” と感じるか**です。これが成立しない場合、価格ではなくオンボーディング・要求項目の粒度・達成演出を先に改善します。

| 指標 | 定義 | ベータでの進行判断 |
| --- | --- | --- |
| 有効化率 | インストール後24時間以内に、必須項目・日課ルール・制限対象の3点を設定した割合 | 設定離脱の画面を特定し、文言または手順を修正する。 |
| 初回価値到達率 | 初回設定から7日以内に、必須条件の達成と制限解除を1回経験した割合 | 低い場合は必須項目の初期テンプレートと初回ガイドを見直す。 |
| 7日継続率 | 初回利用から7日後に、1回以上Todo・習慣を操作した割合 | 価値の継続性を判定する主指標にする。 |
| 安全性 | ブロックループ、端末操作阻害、誤ブロック、権限説明への苦情件数 | P0障害が1件でもあれば公開拡大を止め、修正を優先する。 |
| 支払い意向 | ベータ中にPlus相当の価値へ明示的に関心を示した割合と理由 | 実課金前の定性データとしてプラン境界を調整する。 |

### Phase C：英語版ソフトローンチ（Day 46–70）

英語ストアページで公開し、最初の獲得はASO、短いデモ動画、ユーザーコミュニティ、プロダクト紹介ページに限定します。広告は、7日継続率と初回価値到達率が改善傾向にあるまで小額のテスト以外は行いません。複数のストア説明を試し、訴求を「Block distracting apps」だけに寄せず、**“Finish what matters, then unlock what distracts you.”** の成果文脈で比較します。

初回レビューを急がせたり、特典と引き換えに評価を求めたりしません。ユーザーが少なくとも一度、必須条件を達成して解除体験をした後に、控えめなフィードバック導線を出します。

### Phase D：有料化と拡張（Day 71–90）

7日無料体験付きの年額Plusを有効化します。月額は選択肢として残す一方、年額を既定のおすすめ表示にします。最初の値上げ・値下げは、少なくとも1つの完全な試用→更新サイクルを観測してから判断します。

この段階でのみ、次の順番で成長投資を広げます。

1. **ASO**：キーワード、最初の2枚のスクリーンショット、アクセシビリティ開示の安心感、達成画面をA/B検証する。
2. **紹介**：友人を管理・強制する機能ではなく、「7日間の集中リセット」など共有可能なチャレンジコンテンツを用意する。
3. **コンテンツ**：学生・クリエイター向けに、必須Todoテンプレート、朝・夜の日課テンプレート、設定ガイドを英語と日本語で公開する。
4. **地域・言語**：英語と日本語の定性フィードバックが安定してから、スペイン語またはポルトガル語を追加する。翻訳は権限開示・法的文言・サポート体制と同時に行う。

## 5. プロダクトロードマップ：売上より先に継続価値を強くする

| 時期 | 投資する機能 | 収益への意味 | 後回しにするもの |
| --- | --- | --- | --- |
| v1 公開 | 確実なGate、予定ルール、数値目標、反復、サブタスク、Widget、明確な解除表示 | コアの支払い理由を作る。 | ソーシャル、AI生成、企業管理。 |
| v1.1 | 安全なデータエクスポート、テンプレート、改善済みオンボーディング、フィードバック導線 | 失望を減らし、継続率を改善する。 | 高価なクラウド同期。 |
| v1.2 | オプトインのクラウドバックアップ、端末移行、購読復元の改善 | Plusの継続価値を増やす。 | 無差別な広告ネットワーク。 |
| v2 | iOS Companion、または承認済みentitlementに基づくScreen Time連携 | プラットフォーム拡張の選択肢を持つ。 | Androidと同一の制限を事前に約束すること。 |
| v3 | 学生向け提供、紹介キャンペーン、チーム向け分析の検証 | チャネル多様化を検討する。 | 雇用主が個人端末を強制管理する機能。 |

## 6. 直近7日間の実行順位

1. **商品定義を固定する**：無料とPlusの境界を上表の内容で仮決定し、アプリ内で「何が増えるか」を1画面にする。
2. **審査対応を先に作る**：アクセシビリティの単独開示・同意、解除方法、Privacy Policy草案、Data safety棚卸し、審査用動画を作る。
3. **英語版の初回体験を磨く**：必須Todo作成、対象アプリ選択、権限設定、達成・解除までを3分以内に誘導する。
4. **計測を最小で入れる**：`onboarding_started`、`required_item_created`、`schedule_created`、`accessibility_enabled`、`first_unlock`、`paywall_viewed`、`trial_started`、`subscription_active`だけを、個人内容なしで記録する。
5. **ベータ募集ページを公開する**：対象者、同意事項、既知の制約、解除手順、フィードバックフォームを明記して30〜60人を募集する。

## 7. 意思決定ルール

収益化を始める基準はダウンロード数ではなく、下表の信頼・継続指標です。数値の初期値はベータで観測して更新しますが、事故を見逃さないルールは固定します。

| 判断 | 進める条件 | 停止・修正条件 |
| --- | --- | --- |
| 公開トラック拡大 | 重大なブロックループがなく、権限設定と初回解除をテスターが自力で完了できる。 | システムUI・自アプリを誤って妨害、または解除不能の報告がある。 |
| Plusの実課金化 | 無料版の初回価値到達後に、複数ルール・対象数・自動化への明確な需要が確認できる。 | 無料オンボーディングの離脱が大きく、課金壁が原因で体験できない。 |
| 広告テスト拡大 | 7日継続とサポート負荷が安定し、獲得後の価値到達を追跡できる。 | 継続率が不安定、または広告訴求が「絶対にブロック」など誤認を招く。 |
| iOS Gate開発 | Family Controlsの配布要件、ネイティブ実装能力、明確な需要を満たす。 | entitlement・審査・機能差のいずれかが未解決。 |
