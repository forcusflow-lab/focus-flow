# Focus Flow v12 — 仕様・設計レビュー記録

## 結論

`V12_UX_REDESIGN_SPEC.md`を、現行の保存モデル、集中制限の判定、AndroidウィジェットとExpo Routerの実装境界に照らしてレビューした。実装へ進む前に、時間帯必須が既存の常時制限を意図せず上書きしないこと、時間帯外では解除されること、時間帯を削除した場合に必須の意味が不明確にならないことを明文化した。

| 確認観点 | 検出したリスク | 設計修正 | 実装時の検証 |
|---|---|---|---|
| 常時制限と時間帯必須 | 既存のグローバル必須判定へ時間帯指定項目を混ぜると、時間帯外でも選択アプリが遮断される | 必須項目を「常時」と「時間帯ごと」に分けて要約し、時間帯指定項目は基底の常時ルールに入れない | 19:00前は解除、19:00中は遮断となる単体・統合テスト |
| 既存データ移行 | 古い必須項目の意味が変わる可能性 | 既存`isRequired: true`は`always`へ正規化し、現在の挙動を保持する | 正規化テストで旧データが常時必須になることを確認 |
| 時間帯削除 | 割当済み項目が見えない状態になる、または意図せず常時遮断される | 削除前に影響項目数を明示して確認し、確認後に「いつでも必須」へ変更する | 時間帯削除後に参照IDが残らず、Todayの表示が一致することを確認 |
| 時間帯が未作成 | 必須にしたのに時間帯を選べず、何をすべきか分からない | 必須オン時に時間帯がなければ「いつでも必須」を既定にし、集中制限設定への短い導線を出す | 新規Todo／習慣で空状態と遷移導線を確認 |
| 複数時間帯 | 同じ項目を複数の時間帯で扱えない | 複数選択を許容し、いずれかの選択時間帯が有効なら必須として扱う | 平日朝・夜のいずれでも遮断される境界テスト |
| 日跨ぎ | 22:00–06:00で曜日を誤判定する | 既存の`isScheduleActive`の日跨ぎロジックを共通関数として利用する | 23:00と翌01:00の曜日境界テスト |
| Deep Link | authority形式はExpo RouterでUnmatched Routeになる | URIを`scheme:///`、`scheme:///todos?open=id`、`scheme:///habits?open=id`へ統一する | ネイティブテンプレート、クリーン生成物、実機の3段階で確認 |
| 起動画面 | ネイティブスプラッシュだけでは全画面導入の意図を表せない | 軽量なネイティブ画像の後に、状態復元に連動したアプリ内Launch Overlayを置く。人工的な待機時間は入れない | isReady直後にフェードするコンポーネントテストと実機確認 |

## 実装可能性レビュー

時間帯の定義自体は既に`GateSchedule`にあり、曜日・開始時刻・終了時刻・日跨ぎの判定関数も存在する。そのため、独自の時計計算を画面ごとに作るのではなく、TodoとHabitへ`requiredWindowMode`と`requiredScheduleIds`を追加し、集中制限要約・Today・ウィジェットが共通の判定関数を利用する構成が最も小さく安全である。

また、遮断画面の主操作は個別項目へ遷移させない。遮断理由を把握してから優先順位を選べるよう、常にTodayを開く。個別項目へ行く操作はウィジェット本文とTodayの本文に限定する。

## レビュー結果

本仕様は、以下を前提に実装へ進める。

1. 既存の必須項目は常時必須のまま保つ。
2. 新しい時間帯必須は、選択した時間帯内だけ解除条件に入る。
3. 時間帯外でもTodo・習慣は完了できるが、解除条件としては数えない。
4. 時間帯の削除は影響を通知して確認し、割当済み項目を常時必須へ明示的に戻す。
5. 自動テスト・クリーン生成・署名ビルドでは実装整合性を検証し、Android実機のホーム画面、ウィジェット、アクセシビリティ遮断は受入テストでのみ合格とする。
